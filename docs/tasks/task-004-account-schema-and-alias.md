## 背景与目标

标准科目 Schema 是本产品的核心资产：它决定了「不同年份、不同公司写法不同的科目」能否对齐成同一行。本卡只产出配置与校验，不实现匹配算法（匹配在 TASK-005）。

## 执行步骤

1. 定义 `schema/accounts.yaml`：字段 `code`、`label`、`statement`（income/balance/cashflow）、`aliases[]`、`unit`、`required`、`order`。
2. 覆盖三表核心科目 ≥ 60 个；其中 20 项指标所需科目 100% 覆盖。
3. 实现加载器与校验：code 唯一、别名跨科目不得冲突、必填字段齐全、statement 枚举合法。
4. 增加 schema 版本号与变更记录（PATCH 级迭代，不破坏既有 code）。
5. 编写覆盖率脚本：用评估集三表科目名跑一遍，输出未覆盖清单。

## 交付物

- `schema/accounts.yaml`（≥ 60 科目）
- `schema/loader.py` 加载与校验
- 版本号与变更记录
- 覆盖率脚本与首次覆盖率报告

## 验收标准（布尔判定）

1. YAML 可通过加载校验；人为制造重复 `code` 或跨科目冲突别名时，加载失败并指明冲突位置（文件行号或科目 code）。
2. 三表标准科目数 ≥ 60；20 项指标所需科目覆盖率 100%（脚本断言）。
3. 核心行覆盖率 ≥ 90%：分母为真实财报中「可归因到 60 行核心科目」的标签，输出未命中清单
   > 2026-10-31 修订：原「全量科目名覆盖率 ≥ 95%」在「尚无表格结构还原」的阶段不可测——分母混入了 PDF 换行截断片段与银行 / 保险模板空行（76 个唯一标签）。经用户确认，改为「核心行覆盖率 ≥ 90% + 全量覆盖率仅作参考」。等 PRD P2 表格还原上线后重新度量全量口径。。
4. 修改 YAML 后无需改代码即可生效（重启或热加载均可）。
5. `unit` 取值只允许既定枚举，非法值加载失败。
6. 每个 `code` 的 `label` 与 PRD 20 项指标口径一致（人工抽检 10 条）。

## 评测方案

- 加载校验单测：正常加载、缺字段、重复 code、别名冲突、非法 unit 五类用例。
- 覆盖率脚本：评估集全量科目名 → 命中/未命中统计 → 阈值断言。
- 人工抽检：从 `account_code` 中随机抽 10 条与 PRD 指标定义比对。

## 风险与备注

- 别名表会被长尾写法持续挑战，本卡只要求首版覆盖率达标；提升靠后续 PATCH 迭代，不得为此改动 code 命名。
- 会计政策变更（如新收入准则）可能导致同名科目口径不同，v1.0 不处理口径变更（见 TASK 后续多期对齐卡），只在字段上预留 `caliber_note`。

## 待确认：覆盖率口径（阻塞验收项 3）

现状与原因：

1. 表格结构还原（PRD P2）属于后续任务卡，目前只能用「行首中文串」近似科目名，会把「合并利润表」「单位：元」「归属于母公司所有者权益」（被 PDF 换行截断）等噪声计入分母；
2. 年报三表模板会同时打印银行 / 保险专用空行（拆出资金、保险合同准备金、应收保费等），共 76 个唯一标签，与通用企业无关；
3. 真实缺口仍需补：债权投资、其他债权投资、长期应付职工薪酬、其他非流动金融资产等。

建议改为三条可判定标准（需你确认后我再改本卡）：

- a) 20 项指标所需科目 100% 可解析（已达成）；
- b) 核心行覆盖率 ≥ 90%：分母改为人维护的 60 行核心科目清单（随 schema 版本化），不再用文本行；
- c) 全量行覆盖率仅作为参考指标记录，不设发布门槛，等 P2 表格还原后重新度量。
