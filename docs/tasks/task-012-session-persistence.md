## 背景与目标

当前会话只存在内存里，重启即丢；上传原件也没有生命周期管理。本卡把会话、期次、行、指标、溯源落进 SQLite，并在解析完成后删除原件。

## 执行步骤

1. 存储层：补 `store` 读写接口（session / filing / entry / metric / check / job）。
2. 上传后入库，解析结果入库，页面与接口从库读取（内存缓存可选）。
3. 原件生命周期：上传至 `data/tmp/`，解析成功即删除；失败保留 24 小时供重试。
4. 启动时清理超期临时文件；无主 job 标记 `interrupted`。
5. 一键清空会话：级联删除结构化数据、溯源片段与导出记录。
6. 重启恢复：服务重启后原会话仍可访问，页面数据一致。

## 交付物

- store 读写层与迁移补齐（如需）
- 上传/解析/看板改为读写数据库
- 临时文件清理任务
- 清空会话接口与测试

## 验收标准（布尔判定）

1. 上传解析后重启服务，原会话页面 200 且指标与重启前一致。
2. 解析成功后 `data/tmp/` 中对应原件不存在。
3. 解析失败时原件保留，且 24 小时后被清理任务删除。
4. 删除会话后，其 filing / entry / metric / export 记录全部不存在。
5. 清空操作不影响其他会话（构造两个会话验证）。
6. 页面与 `/metrics`、`/statements` 返回的数据来自数据库（可用改库后刷新验证）。

## 评测方案

- 重启恢复：TestClient 两次构建应用，第二次不注入会话，断言仍可读。
- 文件断言：解析前后检查 `data/tmp`。
- 级联删除：删除后逐表 count 为 0，另一会话不受影响。

## 风险与备注

- 迁移一旦上线只追加，不改历史版本（TASK-001 已定规则）。
- 原件删除是合规承诺，测试必须覆盖「成功路径删除」与「失败路径保留」两条。

## 评测结果（2026-10-31）

| 项 | 结果 |
| ---- | ---- |
| 落库 | session + filing.snapshot（迁移 v2）；重启后页面 200，20 项指标与重启前一致 |
| 原件生命周期 | 解析成功即删除（实测 tmp 为空）；失败保留；启动时清理超过 24 小时的原件 |
| 清空会话 | DELETE 级联删除 session / filing / 导出记录；另一会话不受影响 |
| 重启恢复 | 两次 `create_app` 同一数据库，第二次不注入内存会话仍可读 |
| 测试 | 198 项通过，覆盖率 92.81% |

实现说明（2026-10-31 用户确认）：本卡用「filing.snapshot 快照列」落库，而不是把行 / 指标拆进 entry / metric 表。
理由：v1.0 的读取路径是「整会话渲染」，快照最简单可靠；关系化拆表留待需要按科目查询时再做。
