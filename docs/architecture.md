# 财报透视（finance-agent）架构文档
当前版本：v0.1.0（草案）
关联 PRD：`docs/prd.md` v0.2.0（confirmed）
文档状态：draft，待评审
撰写日期：2026-10-31

> 本文只做架构方案与 ADR，不定义接口、不拆任务、不写代码。
> 接口契约见后续 `docs/api-contract.md`；模块内的函数边界只在此处给出职责说明。

## 1. 架构概述

### 设计原则

1. **解析与呈现解耦**：解析产物是「结构化数据 + 溯源信息」，页面只消费结构化数据，不直接读 PDF。
2. **数字只走脚本**：任何金额、比率、增速都由 Python 计算，LLM 不参与算数，也不改写数字。
3. **显式失败优于猜测**：定位不到、对齐不了、数据缺失，一律显式标注，不静默填 0。
4. **单人可维护**：技术栈尽量收敛到 Python 一套，避免为 MVP 引入 Node 构建链、消息队列、对象存储。
5. **可替换的解析层**：解析器是接口而非实现，v1.1 接入 OCR / MinerU 类引擎时不动上层。

### 核心约束（来自 PRD）

| PRD 决策 | 架构后果 |
| ---- | ---- |
| D2 网页版、零安装 | 需要一个后端服务 + 浏览器端页面；前端不承担业务计算 |
| D3 v1.0 无账号 | 无用户表、无鉴权中间件；用会话 ID + IP 频率限制 |
| D4 文本型 PDF ≤ 400 页 / 50MB | 解析在服务端完成；单文件解析耗时是核心指标 |
| D5 多期 ≤ 5 期 | 数据模型必须区分「会话」与「期次」，指标按会话聚合 |
| D6 页码 + 片段溯源 | 解析时必须记录 page 与原文片段，随结构化结果一起入库 |
| D7 脚本算数 | 指标计算模块独立，且有单元测试与金标评测 |
| D9 原件不留存 | 原件只进临时目录，解析完成即删；结构化结果独立存储 |
| D10 禁用词零出现 | 文案模板化，LLM 只产出受控枚举，不做自由文本 |

## 2. 模块划分

| 模块 | 职责 | 依赖 | 对应 PRD 功能 |
| ---- | ---- | ---- | ---- |
| `web` | 路由、模板渲染、静态资源；上传入口与页面 | ingest、store、dashboard | U1～U3、V1～V10 呈现 |
| `ingest` | 文件校验（格式 / 大小 / 页数）、临时落盘、会话创建、原件清理 | store、parse 任务投递 | U1～U3 |
| `parse` | 文本层抽取、表格识别、三表定位、数值归一（单位/符号/空值） | 无业务依赖，纯函数为主 | P1～P4 |
| `schema` | 标准科目定义（YAML）+ 别名映射表版本化 | 无 | A1 的输入 |
| `align` | 规则匹配 → 模糊匹配 → LLM 候选 → 待确认清单；多期对齐 | schema、llm | A1～A3 |
| `metrics` | 20 项指标、同比环比、三表勾稽、口径文本 | store、schema | M1～M4 |
| `anomaly` | 规则库（≥8 条）、证据装配、中性措辞 | metrics、store | R1～R3 |
| `dashboard` | 把指标序列装配成 10 组图表数据 | metrics、anomaly | V1～V10 |
| `trace` | 页码 / 片段 / 单位换算说明 / 口径的查询 | store | T1～T3 |
| `export` | Markdown 报告、Excel 明细 | dashboard、store | X1～X3 |
| `jobs` | 任务状态机、进度、超时、重试 | store | 5.2 / 5.3 |
| `ops` | 结构化日志、运行摘要、健康检查、频率限制 | core | 5.5 |

依赖方向单向：`web → dashboard/export → metrics/anomaly → align → parse`；`store` 是横切依赖，任何模块都可读写，但**不允许** `parse` 反向依赖 `web`。

## 3. 数据流

```text
浏览器上传 PDF
   │
   ▼
[ingest] 校验 → 临时目录 → 建 session/filing 记录 → 投递解析任务
   │
   ▼
[parse] 文本层抽取 → 表格识别 → 三表定位 → 数值归一
   │        每取到一个数字：记录 (page, bbox, 原文片段)
   ▼
[align] 规则表匹配 → 模糊匹配 → LLM 候选（仅剩未命中项）→ 待确认清单
   │        多期：按会话把同一标准科目排成时间序列
   ▼
[metrics] 20 项指标 → 同比环比 → 三表勾稽 → 口径文本
   │
   ▼
[anomaly] 规则命中 → 证据（数值 + 页码）→ 中性文案
   │
   ▼
[store] 落库（结构化结果 + 溯源片段）→ 删除原件
   │
   ▼
[web/dashboard] 读库 → 10 组图表数据 → 渲染页面
   │
   ▼
[export] Markdown / Excel
```

关键点：

- 原件删除发生在**落库成功之后**；落库失败则保留原件供重试，但最长保留 24 小时。
- 任何一步失败，`filing.status` 落到 `failed` 并带错误码与「哪一页、哪张表」，不产生部分结果。
- 多期对齐是会话级动作，单期解析完即可先看单期视图。

## 4. 技术选型

| 组件 | 选型 | 理由 |
| ---- | ---- | ---- |
| 运行时 | Python 3.11 | 解析与计算生态最全；与 LLM SDK 同栈 |
| Web 框架 | FastAPI + Jinja2 服务端渲染 | 单人维护；上传/进度/页面同进程，省一套前端构建 |
| 前端交互 | 原生 JS + 自托管 ECharts 5 | 原型已验证可行（8 图、弹层、Tab 全用原生实现）；不引入 React/Vite |
| PDF 文本层 | pypdfium2 | Apache/BSD 许可，渲染与页级信息稳定 |
| 表格抽取 | pdfplumber（pdfminer.six） | MIT 许可；文本型 PDF 的表格线/文本对齐能力够用 |
| 数据存储 | SQLite 3.35+（WAL 模式） | 单机够用；零运维；结构化结果与溯源片段同库 |
| 任务执行 | asyncio + 进程池（CPU 密集部分） | 无 Redis/Celery；任务状态落库，重启可恢复 |
| LLM | 云端 API（DeepSeek / Qwen 类），可配置关闭 | 只做科目候选生成；无 Key 时自动降级 |
| 配置 | pydantic-settings + `.env` | 与 PRD 的密钥管理要求一致 |
| 测试 | pytest + 评测脚本（`tests/eval`） | 金标回归，对应 PRD 附录 A |
| 部署 | Docker Compose + Nginx（TLS 终止） | 单机一键起；后续可换托管 |
| 日志 | structlog 风格 JSON 日志 | 运行摘要与告警所需字段结构化 |

**明确不用**：Node 构建链、React/Vue、Celery/Redis、Postgres、对象存储、Kubernetes。理由见 ADR。

## 5. 数据模型（概念级）

| 表 | 关键字段 | 说明 |
| ---- | ---- | ---- |
| `session` | id、created_at、company_name、filing_count、status | 一次上传会话，可含多期 |
| `filing` | id、session_id、report_type、period、pages、status、error_code | 单期财报 |
| `cell` | filing_id、page、table_kind、row_no、col_no、text、bbox | 解析出的原始单元格（保留原文） |
| `entry` | filing_id、account_code、value、unit、page、snippet、confidence、source | 对齐后的标准科目值；`source=rule/fuzzy/llm/manual` |
| `metric` | filing_id、code、value、unit、formula、missing_reason | 计算指标；不可算时写 `missing_reason` |
| `check` | filing_id、rule、passed、diff | 勾稽校验结果 |
| `anomaly` | session_id、rule_code、evidence_json、page_refs、text | 异常项与证据 |
| `job` | id、filing_id、state、progress、attempts、error、started_at、finished_at | 任务状态机 |
| `export` | session_id、kind、status、created_at | 导出记录（文件短期存在） |

约定：

- `entry.value` 与 `metric.value` 一律存**标准单位与标准符号**（元、支出为负）。
- `entry.snippet` 存原文片段（≤ 200 字），是溯源弹层的数据源。
- 任何 `entry` 没有 `page` 与 `snippet` 时，不得进入看板与导出（对应 T3）。
- `account_code` 来自版本化的 `schema/accounts.yaml`，变更走 PATCH 版本记录。

## 6. 部署结构

```text
单台服务器
├── Nginx          TLS / 反向代理 / 上传大小限制
├── uvicorn        FastAPI 应用（1 个 worker，多线程处理请求）
├── 解析进程池      2～4 个 worker（CPU 密集，隔离内存）
├── SQLite 文件     ./data/app.db（WAL）
└── 临时目录        ./data/tmp（原件，解析后删除）
```

- v1.0 单实例；并发上限 5 个解析任务，超出排队并在页面显示位次。
- 原件目录与数据库分离挂载，便于备份与清理。
- 升级方式：替换镜像 + 重启；任务状态落库，重启后未完成任务标记为 `interrupted` 并可重试。
- 不做多实例横向扩展（见 ADR-007），v1.1 若并发不够再评估。

## 7. 风险与约束

| 风险 | 影响 | 应对 |
| ---- | ---- | ---- |
| 财报版式长尾（无边框表、跨页表、横向页） | 抽取准确率不达标 | 评估集覆盖版式；未对齐显式化；v1.1 评估 OCR |
| 纯 Python 抽取 300 页耗时 | 首屏 60 秒门槛吃紧 | 先解析三表页范围再抽全表；进程池并行；必要时把门槛提到 120 秒 |
| 扫描件 / 图片型 PDF | 无法解析 | 识别并明确降级提示；不编造数字 |
| LLM 不可用或超时 | 科目对齐覆盖率下降 | 规则表 + 模糊匹配打底；LLM 失败只影响覆盖率 |
| 许可证 | 商用分发受阻 | 只用 MIT/Apache/BSD 许可的解析库；ADR-002 记录被排除项 |
| 单机写并发 | 多任务同时写 SQLite 冲突 | WAL + 单写队列；v1.0 并发上限 5 |
| 合规文案 | 输出越界成投资建议 | 模板化文案 + 禁用词机器校验（发布门槛） |
| 原件留存 | 隐私与合规风险 | 解析后删除 + 24 小时兜底清理任务 |

## 8. ADR 记录（追加式，不修改历史）

### ADR-001 前端采用服务端渲染 + 原生 JS，不引入 SPA 框架

- 上下文：页面需要上传、进度、8 组图表、Tab 切换、溯源弹层；团队为单人。
- 备选方案：
  1. React/Vue SPA + 构建链：交互扩展性强，但引入 Node 工具链、构建产物与两套依赖，单人维护成本高。
  2. 服务端渲染 + 原生 JS + ECharts：一套 Python 栈；原型已验证 8 图与弹层可行。
- 决策：选定方案 2。
- 取舍：复杂交互（拖拽排序、虚拟列表）实现成本高；页面状态靠 URL 与少量 JS 维护。
- 遗留风险：v1.1 若加账号与历史库，页面状态变多，可能触到原生 JS 维护上限，届时再评估局部引入轻量框架。

### ADR-002 PDF 解析使用 pdfplumber + pypdfium2，排除 PyMuPDF 与 MinerU 类重引擎

- 上下文：目标文档是文本型 A 股财报；需要表格结构、页码与原文片段；未来可能商用分发。
- 备选方案：
  1. PyMuPDF：抽取快、能力强，但 AGPL / 商业双授权，闭源分发需购买商业许可。
  2. MinerU 类版面模型：对扫描件与复杂版式最强，但依赖模型权重、体积大、部署重，且许可证随版本变动需核实。
  3. pdfplumber + pypdfium2：MIT / Apache 许可，文本型 PDF 的表格线识别够用，零模型依赖。
- 决策：选定方案 3；解析器定义为接口，v1.1 可在接口后接入 OCR / 重引擎。
- 取舍：无边框表、扫描件能力弱；需要自研坐标聚类与跨页拼接规则。
- 遗留风险：若后续用户强烈需要扫描件，需重新评估许可证与算力成本。

### ADR-003 存储使用 SQLite（WAL），不引入 Postgres 与对象存储

- 上下文：单机、单用户量级、结构化结果 + 溯源片段；原件不留存。
- 备选方案：
  1. Postgres：并发与扩展性好，但多一个运维组件，v1.0 无必要。
  2. SQLite WAL：零运维、单文件备份、读并发好。
- 决策：选定方案 2。
- 取舍：写并发受限，需要单写队列；跨机扩展困难。
- 遗留风险：若解析任务并发提升到 20+，写锁会成为瓶颈，需迁移 Postgres（届时走 ADR 追加）。

### ADR-004 任务执行使用进程内状态机，不引入 Celery/Redis

- 上下文：v1.0 单实例、并发 5、任务可重试、需要进度展示。
- 备选方案：
  1. Celery + Redis：成熟，但引入两个额外服务与部署复杂度。
  2. 进程内 asyncio + 解析进程池，任务状态落库：零额外组件，重启可恢复。
- 决策：选定方案 2。
- 取舍：无跨机调度；进程崩溃时任务需靠状态机标记 `interrupted` 后重试。
- 遗留风险：v1.1 若多实例部署，需要外置队列，届时追加 ADR。

### ADR-005 LLM 只用于科目映射候选，文案模板化

- 上下文：科目写法长尾需要语义能力；但输出必须可控且禁用词零出现。
- 备选方案：
  1. LLM 生成摘要与解读：表达自然，但不可控、易越界、成本高。
  2. LLM 仅对未命中科目给出候选标准科目（受控枚举），文案全部模板化。
- 决策：选定方案 2；未命中且候选置信度低时进入「待确认」，不猜。
- 取舍：页面文案较模板化；覆盖提升依赖别名表与模糊匹配质量。
- 遗留风险：LLM 供应商变更导致映射质量波动，需在运行摘要中记录模型与版本。

### ADR-006 溯源在解析期记录页码与原文片段，v1.0 不做坐标跳转

- 上下文：PRD 要求每个数字可回溯原文；坐标级跳转成本更高。
- 备选方案：
  1. 页码 + 片段：实现简单，解析期顺手记录，可满足「核对」诉求。
  2. 坐标高亮 + PDF 内跳转：体验更好，但需要 PDF 渲染前端与坐标精度保障。
- 决策：v1.0 选定方案 1；数据库预留 `bbox` 字段，v1.1 升级为坐标跳转不做迁移破坏。
- 取舍：用户核对需要手动翻页到对应页码。
- 遗留风险：片段截取可能截断上下文，需固定截取策略（同行 + 相邻两行）。

### ADR-007 部署为单机 Docker Compose + Nginx，v1.0 不做多实例

- 上下文：v1.0 无账号、并发 5、目标是尽快验证需求。
- 备选方案：
  1. 云托管 + 多实例 + 负载均衡：可用性高，但成本与复杂度不符合验证阶段。
  2. 单机容器化：一键部署、成本低、升级简单。
- 决策：选定方案 2。
- 取舍：无高可用；服务器故障期间不可用。
- 遗留风险：验证成立后需规划多实例与对象存储迁移，届时追加 ADR。

### ADR-008 图表按多年趋势重构为 10 图，自由现金流只在展示层衍生

- 上下文：用户最看重的 9 项指标（扣非净利润、经营现金流、ROE、毛利率、净利率、资产负债率、应收 / 存货周转率、自由现金流）需要在多年年报序列上直接读出变化；现 7 图存在同轴混单位、现金流无正负配色、FCF 无数据源等问题。
- 备选方案：
  1. 11 项指标扩到 21 项、FCF 进指标卡与金标评测：口径统一，但会改动对外承诺的 20 项指标契约、对比台与 200 个金标用例。
  2. FCF 只在 `dashboard.charts` 展示层衍生（经营现金流 − 购建长期资产支付的现金），指标卡维持 20 项：契约不变，图上标注口径。
- 决策：选定方案 2；周转率同理，由已有周转天数换算（365 ÷ 天数），指标卡仍显示天数。
- 取舍：同一条 FCF 在图表与导出中口径需重复说明；后续若要进指标卡，需另开任务扩展指标契约。
- 遗留风险：购建长期资产科目未披露时 FCF 为空，图 6 只画经营现金流并提示。
